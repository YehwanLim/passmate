# 결제 이용권 보유자 분석 처리량 설계

**상태:** 사용자 승인 설계, 구현 전 검토

## 목표

정상적으로 여러 장의 결제 이용권을 보유한 사용자가 짧은 시간에 여러 자소서를 분석할 수 있게 하되, 계정 탈취·자동화·오작동으로 AI 호출과 비용이 급증하지 않게 한다.

## 정책

| 서버가 확인한 상태 | 15분당 분석 접수 | 동시에 진행 가능한 분석 |
| --- | ---: | ---: |
| 무료 이용권만 보유 | 3회 | 1개 |
| 활성화된 결제 이용권이 1장 이상 남음 | 10회 | 2개 |

- 이용권은 기존 예약(`PENDING`) → 성공 확정(`CONSUMED`) → 실패 취소(`CANCELLED`) 흐름으로 정확히 한 장씩 처리한다.
- 같은 idempotency key 재전송은 새 분석·새 이용권·새 rate-limit 카운트를 만들지 않는다.
- 현재 베타는 `premiumEnabled=false`이므로 모든 사용자는 무료 정책을 사용한다. 결제 CTA, 구매 의도 변경, Groble 웹훅은 이번 범위에서 계속 비활성이다.
- 결제 이용권 정책은 향후 결제 연동을 별도 보안 검증 후 활성화했을 때만 자동으로 적용된다.

## 신뢰 경계와 판정 방식

클라이언트는 이용권 수, 결제 여부, 처리량 등급을 보내지 않는다. 서버가 인증 토큰의 사용자 ID로만 다음을 읽는다.

1. `EntitlementSetting.premiumEnabled`
2. `AnalysisEntitlement`의 부여된 결제 이용권
3. `AnalysisReservation`의 `PENDING`·`CONSUMED` 사용량

`premiumEnabled=true`이고 남은 결제 이용권이 하나 이상일 때만 결제 정책을 선택한다. 그렇지 않으면 무료 정책을 사용한다. 결제 이용권이 모두 소진되면 새 분석은 이용권 소진 오류로 끝나며, rate-limit 정책 변경으로 추가 호출을 허용하지 않는다.

## 서버 처리 순서

`POST /api/analyze`는 다음 순서를 따른다.

1. 인증, 입력값, idempotency key, kill switch를 확인한다.
2. 기존 idempotency 요청 또는 같은 내용의 미완료 요청을 먼저 반환한다. 이 경로는 새 이용권이나 rate-limit 카운트를 소비하지 않는다.
3. 하나의 DB 트랜잭션에서 사용자별 이용권 행을 잠그고, DB의 이용권 상태로 무료/결제 정책을 고른 뒤 `PENDING`·`CALLING`·`PERSISTENCE_PENDING` 분석 요청 수를 센다.
4. 동시 처리 한도(무료 1, 결제 2)를 초과하면 `409 ANALYSIS_CONCURRENCY_LIMITED`를 반환한다. 이 경우 rate-limit bucket, 이용권 예약, 프로젝트, 분석 요청 모두 변경하지 않으며 AI도 호출하지 않는다.
5. 한도 안일 때만 같은 트랜잭션에서 공유 Postgres rate-limit bucket을 증가시킨다. 초과 시 `429 RATE_LIMITED`와 `Retry-After`만 반환하며 AI는 호출하지 않는다.
6. rate-limit도 통과하면 이용권 예약, 프로젝트·분석·분석 요청 생성을 같은 트랜잭션으로 확정하고, 기존 background lifecycle에 넘긴다.

사용자별 이용권 행 잠금 안에서 정책 선택·동시성 검사·rate-limit 증가·예약을 수행하므로, 거의 동시에 들어온 두 요청도 둘 다 빈 자리를 보았다고 판단해 한도를 넘는 경쟁 상태가 생기지 않는다. 진행 중인 작업 때문에 거절된 재시도는 15분 rate-limit 횟수를 소모하지 않는다.

## 사용자 경험과 오류 계약

- `RATE_LIMITED`(429): 제목 `요청 제한`, 재시도까지 남은 시간을 `Retry-After`로 안내할 수 있다.
- `ANALYSIS_CONCURRENCY_LIMITED`(409): 제목 `분석 진행 중`, 무료는 한 건·결제 이용권 보유자는 두 건이 끝난 뒤 재시도하도록 안내한다. 세부 이용권·모델·DB 정보는 노출하지 않는다.
- `ANALYSIS_CREDITS_EXHAUSTED`(409): 베타 무료 1회 소진 또는 결제 이용권 소진을 안전한 문구로 안내한다.
- 접수된 요청은 기존과 같이 `202`와 안전한 receipt만 반환하고, `/api/analysis-requests/:id`의 소유자 전용 polling으로 결과를 연다.

## 데이터·배포 범위

- 새 테이블이나 schema migration은 필요 없다. 기존 `analysis_entitlements`, `analysis_reservations`, `analysis_requests`, `api_rate_limit_buckets`만 사용한다.
- 정책 선택과 동시성 검사 함수는 서버 전용 모듈로 둔다.
- 기존 RLS 기본 거부, 사용자 소유권 조건, 관리자 kill switch, idempotency, 감사 로그의 민감 원문 미보관 정책을 변경하지 않는다.
- 결제 공급자 서명 검증·통화·금액·replay 계약은 이번 변경의 범위 밖이며, 별도 릴리스 전까지 재도입하지 않는다.

## 검증 기준

1. 무료 상태에서 세 번째 접수까지 허용되고 네 번째는 `RATE_LIMITED`이며 모델 호출이 없다.
2. 결제 이용권이 남은 상태에서는 같은 15분 bucket에서 열 번째 접수까지 허용되고 열한 번째는 `RATE_LIMITED`이다.
3. 무료 사용자는 서로 다른 내용의 미완료 요청을 두 개 만들 수 없고, 결제 이용권 보유자는 정확히 두 개까지만 가능하다.
4. 동시 요청 경쟁 테스트에서 무료는 최대 한 개, 결제 이용권 보유자는 최대 두 개만 `PENDING` 이상 상태가 된다.
5. idempotency 재전송, 분석 실패·취소, kill switch, 타인 요청 조회는 기존 보안 계약을 유지한다.
6. 브라우저는 opaque 오류 코드에만 정해진 안내를 표시하고, 이용권 수·사용자 식별자·원문·공급자 오류를 표시하거나 로그에 남기지 않는다.

## 비목표

- 이번 변경으로 Premium 결제, 구매 화면, 웹훅 또는 실제 과금은 활성화하지 않는다.
- 전역 일일 비용 예산·조직 단위 quota는 별도의 운영 기능으로 다룬다.
