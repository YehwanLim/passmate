# 프로필 메뉴와 이용권 진입점 설계

## 목적

로그인한 사용자가 랜딩 페이지 상단의 프로필 메뉴에서 자신의 지원서와 이용권 관리 화면으로 바로 이동할 수 있게 한다. 결제는 별도 메뉴로 분리하지 않고, 이용권 화면 안에서 현재 잔여 분석 횟수를 확인한 뒤 필요할 때 시작한다.

## 범위

- 로그인 상태의 공통 `AuthButton` 드롭다운을 확장한다.
- 로그인된 사용자를 위한 `/entitlements` 화면을 추가한다.
- 기존 인증된 이용권 API와 구매 의도 생성 API를 화면에 연결한다.

이번 변경에는 결제 상품, 이용권 산정 규칙, 웹훅, 관리자 결제 화면을 새로 만들거나 수정하지 않는다.

## 사용자 경험

### 프로필 메뉴

로그인 상태에서 프로필 버튼을 누르면 다음 항목을 순서대로 표시한다.

1. 현재 사용자 이름과 이메일
2. `내 지원서` — `/my`로 이동
3. `이용권` — `/entitlements`로 이동
4. 구분선
5. `로그아웃`

메뉴 항목을 선택하면 드롭다운을 즉시 닫고 해당 화면으로 이동한다. 기존 외부 클릭 닫기, `aria-expanded`, 로그아웃 중 비활성 상태는 유지한다.

### 이용권 화면

`/entitlements`는 로그인 보호 화면이다. 인증 확인이 끝난 뒤 `GET /api/entitlements`를 요청해 서버가 계산한 값을 표시한다.

- 총 남은 분석 횟수
- 무료 이용권의 지급·사용·잔여 횟수
- 프리미엄 이용권의 지급·사용·잔여 횟수
- 프리미엄 판매가 활성화되어 있고 결제 URL이 준비된 경우에만 `결제하기` 버튼

`결제하기`는 `POST /api/entitlements/purchase-intents`로 구매 의도를 먼저 만든다. 성공하면 응답의 `checkoutUrl`로 현재 탭을 이동한다. 구매 의도 생성이 거부되거나 실패하면 화면에 이해 가능한 오류 메시지를 표시하고 현재 화면에 머문다. 결제 완료 복귀만으로 이용권을 추가하지 않으며, 기존 웹훅 지급 규칙을 그대로 따른다.

로딩 중에는 상태 카드의 자리표시자를, 조회 실패 시에는 재시도 가능한 오류 상태를 보여 준다. 이용권 조회 결과가 없거나 `0`인 경우도 정상 상태로 표시한다.

## 데이터와 경계

클라이언트는 이용권 잔여 횟수를 브라우저 저장소에서 계산하거나 보정하지 않는다. `/api/entitlements` 응답을 표시 전용으로 사용하고, 구매는 서버가 생성한 구매 의도와 결제 URL로만 시작한다.

`/entitlements`의 비로그인 접근은 기존 `useRequireAuth` 규칙에 따라 `/login?redirect=%2Fentitlements`로 보낸다. 프로필 드롭다운은 이미 인증된 상태에서만 표시되므로 메뉴 항목 자체에 별도 로그인 처리를 추가하지 않는다.

## 구현 경계

- `client/src/components/AuthButton.tsx`: 메뉴 항목과 키보드/마우스 상호작용을 추가한다.
- `client/src/pages/Entitlements.tsx`: 이용권 조회·상태·구매 전환 UI를 담당한다.
- `client/src/App.tsx`: `/entitlements` 라우트를 등록한다.
- 관련 단위 테스트: 메뉴의 목적지, 이용권 상태와 구매 요청/오류 동작을 검증한다.

기존 `/my` 지원서 관리 화면, 랜딩 상단 네비게이션, 이용권 API 및 결제 웹훅은 변경하지 않는다.

## 검증 기준

- 로그인한 사용자가 랜딩 페이지 프로필 메뉴에서 `내 지원서`와 `이용권`으로 이동할 수 있다.
- 비로그인 상태에서는 프로필 메뉴 대신 기존 로그인 버튼만 보인다.
- 이용권 화면은 서버 응답의 무료·프리미엄·총 잔여 횟수를 표시한다.
- 결제 가능 조건일 때만 결제 버튼을 보여 주며, 클릭 시 구매 의도 생성 후 결제 URL로 이동한다.
- 구매 의도 생성 실패와 이용권 조회 실패는 화면에 오류로 표시되고 앱이 중단되지 않는다.
- 기존 로그아웃 및 지원서 관리 동작이 유지된다.
