# 경험 자동 채우기 설계 (2026-10-08)

## 배경

경험 관리는 Pre:View의 새 핵심 기능이다. 지금은 경험 금고에 경험을 **손으로 하나씩** 적어야 한다(제목·기간·상황·한 일·결과·키워드). 처음 온 사용자는 금고가 0개인 상태에서 멈추기 쉽고, 금고가 비면 경험→초안도 쓸 수 없다.

이 기능은 예전에 쓴 자소서를 붙여 넣거나 파일로 올리면 AI가 경험 후보를 뽑아 주고, 사용자가 골라서 금고에 저장하게 한다. 원칙은 경험→초안과 같은 **"부풀리지 않는 AI"**다. 원문에 쓰인 사실만 옮기고, 없는 내용은 빈칸으로 둔다.

## 1. 사용자 흐름

1. 마이페이지 "내 경험" 탭 맨 위에 **"예전 자소서에서 경험 가져오기"** 버튼을 둔다. 금고가 0개면 빈 화면 안내 아래에 같은 버튼을 크게 둔다.
2. 버튼을 누르면 창이 열린다.
   - 텍스트를 붙여 넣는 칸과 "PDF·Word 파일 올리기" 버튼이 있다. 파일 글자 추출은 `client/src/lib/resumeFileImport.ts`의 `extractTextFromFile`을 그대로 쓴다.
   - 받는 길이는 200자 이상, 20,000자 이하다. 글자 수와 "하루 3번까지 무료" 안내를 보여 주고, 한 번 뽑은 뒤에는 서버가 준 남은 횟수("오늘 N번 남았어요")로 바꾼다.
3. **"경험 뽑기"**를 누르면 대기 문구 "자소서에서 경험을 찾고 있어요"가 보인다. 보통 5~10초 걸린다.
4. **후보 카드**가 최대 8개 나온다.
   - 칸: 제목·기간·상황·한 일·결과·키워드. 금고 수정 화면과 같은 입력칸이라 카드 안에서 바로 고칠 수 있다.
   - 비어 있는 칸은 연한 노란 바탕에 "직접 채워 주세요"를 보여 준다.
   - 카드 맨 아래에는 근거 원문 문장을 회색 작은 글씨로 둔다(`원문: …`).
   - 금고에 비슷한 제목이 이미 있으면 "비슷한 경험이 이미 있어요"를 보여 주고, 체크를 꺼 둔 채로 시작한다.
   - 나머지 카드는 체크된 채로 시작한다.
5. **"선택한 N개 저장"**을 누르면 한 번에 저장하고 창을 닫는다. 금고 목록은 새로고침한다.
6. 뽑기에 실패하거나 0개를 찾으면 안내를 보여 주고, 오늘 횟수는 돌려준다.

휴대폰에서는 창이 화면 전체를 쓴다. 카드는 한 줄에 하나씩, 저장 버튼은 아래에 고정한다.

## 2. 서버

### 2.1 엔드포인트: `POST /api/analyze/extract`

- 배포 경로는 `api/analyze.js?extract=1`이다. 기존 `selectAnalyzeHandler`에 `extract` 갈래를 추가하므로 Vercel 함수 수는 늘지 않는다(함정 2).
- `vite.config.ts`의 `apiRoute()`에 `/api/analyze/extract → { file: "api/analyze.js", query: { extract: "1" } }` 매핑을 추가한다(함정 1).
- `vercel.json`의 rewrite와 `deployment-security` 테스트에 `/api/analyze/extract`를 추가한다. 경험→초안 때 `/api/analyze/draft`를 추가한 것과 같은 방식이다.
- 새 파일은 `lib/experience-extract.js`다. `createExperienceExtractHandler({ db, requireUser, callModel, consumeRateLimit, refundRateLimit, now })`로 의존성을 주입하는 팩토리 패턴을 쓴다(경험→초안과 같다).

**요청**: `{ "text": string }`

**처리 순서**
1. 메서드가 POST가 아니면 405.
2. `requireActiveApplicationUser`. 비로그인은 401.
3. 입력 검사: `text`가 문자열인지, `sanitizeInput` 후 공백 정리, 200자 이상 20,000자 이하인지. 아니면 400 `INVALID_REQUEST`.
4. 금고가 이미 100개(`EXPERIENCE_LIMITS.perUser`)면 409 `EXPERIENCE_LIMIT_REACHED`. 모델은 부르지 않는다.
5. 레이트리밋: `USER_RATE_LIMITS.experienceExtract = { route: "experience-extract", limit: 3, windowMs: 24h }`. 넘으면 429(`sendRateLimited`, 기존 형태).
6. 모델 호출. 모델 오류·시간 초과·JSON 파싱 실패면 횟수를 돌려주고 502 `EXTRACT_FAILED`.
7. 출력 정리(2.3). 0개면 횟수를 돌려주고 200 `{ candidates: [], remaining }`.
8. 200 `{ candidates: Candidate[], remaining: number }`.

**Candidate**
```ts
{
  title: string;              // 1~100자
  period: string;             // 0~50자, 없으면 ""
  situation: string;          // 0~1500자
  action: string;             // 0~1500자
  result: string;             // 0~1500자
  tags: string[];             // 0~5개, 각 20자 이하
  quotes: string[];           // 1~2개, 원문에 실제로 있는 문장
}
```

`remaining`은 오늘 남은 횟수다. 첫 호출 전에는 "하루 3번까지 무료"로만 안내하고, 호출 뒤부터 `remaining`으로 "오늘 N번 남았어요"를 보여 준다. 남은 횟수만 보려고 새 GET을 만들지 않는다.

### 2.2 모델과 프롬프트

- 모델은 `gemini-2.5-flash`(경험→초안과 같다). 시간 제한은 30초다. 호출은 `lib/model-client.js`의 `callGeminiGenerate`, 파싱은 `parseModelJsonTolerant`를 쓴다.
- 프롬프트는 새 파일 `shared/prompts/extractPrompt.js` 한 곳에만 정의한다. 단일 정의처 테스트(`reportPrompt.singleSource.test.ts`)가 이 파일을 막지 않는지 함께 확인한다(함정 7).
- 응답은 `responseSchema`(JSON)로 강제한다. 금지 규칙은 규칙 목록이 아니라 **각 필드 설명**에 넣는다(메모리: flash-lite·flash 모두 필드 설명을 더 잘 따름). 금지 예시 단어는 모델이 베끼므로 넣지 않는다.
  - `title`: 이 경험을 한 줄로 부르는 이름. 원문 표현을 살리고 평가어("성공적인", "탁월한")를 붙이지 않는다.
  - `situation` / `action` / `result`: 원문 문장을 거의 그대로 옮긴다. 원문에 없는 내용은 빈 문자열로 둔다. 동기·감정·팀원 반응을 지어내지 않는다.
  - `period`: 원문에 기간·날짜가 있을 때만 적는다.
  - `tags`: 원문에 나온 역량·도메인 단어 최대 5개.
  - `quotes`: 이 경험의 근거가 된 원문 문장 1~2개. 한 글자도 바꾸지 않고 복사한다.
- 후보는 최대 8개다. 한 경험을 여러 문항에서 다시 쓴 경우에는 하나로 합친다.

### 2.3 출력 정리 (`normalizeExtractOutput(output, { sourceText })`)

모델 지시는 어겨질 수 있으므로 서버가 결과를 검사한다.

1. 형태 검사: `candidates` 배열이 아니면 빈 배열로 본다.
2. **근거 확인**: 원문과 `quote` 모두에서 공백·줄바꿈을 지운 뒤 포함 여부를 본다. 원문에 있는 `quote`만 남기고, 남은 `quote`가 0개인 후보는 버린다.
3. **숫자 확인**: 원문에 없는 숫자는 `[실제 수치]`로 바꾼다. `lib/experience-draft.js`의 숫자 검사(`numberCores`·`guardNumbers`, 점 날짜 인정)를 공용 함수로 꺼내 두 곳에서 같이 쓴다. 꺼낼 곳은 `lib/number-guard.js`다. 호출자가 둘이 되므로 꺼낼 근거가 있다.
4. **길이·형식**: 칸마다 `sanitizeInput`, 공백 정리, `EXPERIENCE_LIMITS` 길이로 자른다. 태그는 중복을 지우고 5개까지만 남긴다.
5. 제목이 빈 후보는 버린다. 8개를 넘으면 앞의 8개만 남긴다.

### 2.4 여러 개 한꺼번에 저장

기존 `POST /api/account/experiences`(`lib/experiences.js`)를 넓힌다. 새 경로는 만들지 않는다.

- 본문이 `{ experiences: [...] }`이면 여러 개를 저장한다(1~8개). 각 항목은 기존 `normalizeExperience(item, { partial: false })`로 검사하고, 하나라도 틀리면 전체를 400으로 거절한다.
- 지금 개수 + 새 개수가 100을 넘으면 409 `EXPERIENCE_LIMIT_REACHED`로 전체를 거절한다. 응답에 `available`(더 넣을 수 있는 개수)을 담는다.
- 저장은 `db.$transaction`으로 묶어 전부 저장하거나 하나도 저장하지 않는다. 응답은 201 `{ experiences: Experience[] }`다.
- 지금처럼 본문이 단일 객체인 요청은 그대로 동작한다.
- 클라이언트는 `quotes`를 저장 요청에 넣지 않는다. 금고 모델(`Experience`)은 바꾸지 않는다. **스키마 변경과 마이그레이션은 없다.**

### 2.5 로그·보안

- 자소서 본문, 후보 내용, AI 응답은 로그·감사 이벤트에 남기지 않는다. 남기는 건 결과 종류(`ok` / `empty` / `failed`)와 후보 개수뿐이다.
- 소유권: 저장은 로그인 사용자의 `userId`로만 만든다. 요청 본문에 `userId`가 와도 쓰지 않는다(`normalizeExperience`가 모르는 키를 거절한다).

## 4. 테스트와 검증

**서버** (`tests/api/`, `tests/helpers/http.js`의 `createResponse()` 사용, 실제 AI 호출 없음)
- `experience-extract`
  - 401, 405, 400(짧음·김·문자열 아님), 409(금고 꽉 참, 모델 호출 없음), 429
  - 근거 없는 후보 제거, 공백이 달라도 근거로 인정
  - 원문에 없는 숫자 → `[실제 수치]`, 날짜 숫자는 유지
  - 8개 상한, 칸 길이 자르기, 제목 빈 후보 제거
  - 0개·모델 오류·시간 초과일 때 횟수 돌려주기(`refundRateLimit` 호출 확인)
  - 로그에 본문 없음
- `experiences` 여러 개 저장
  - 전부 저장, 항목 하나만 틀려도 전체 400, 100개 초과면 409와 `available`, 트랜잭션 사용, 단일 객체 요청 하위 호환
- `analyze` 라우터: `?extract=1` 갈래 선택, `vite.config.ts` 매핑, `vercel.json` rewrite, 함수 개수 테스트

**화면** (같은 폴더 Vitest)
- 붙여넣기 → 후보 → 체크·수정 → 저장 흐름
- 비슷한 제목은 체크 해제로 시작
- 빈칸 표시, 오류 문구, 200자 미만이면 버튼 막힘

**기본 검사**: `pnpm check`, 대상 테스트, 위험이 큰 변경이니 전체 vitest.

**실제 품질 확인** (로컬, 진짜 모델)
- 예시 리포트 자소서 2개와 길이·구성이 다른 가짜 자소서 3개를 쓴다. 실제 사용자 자소서는 쓰지 않는다.
- 확인할 것: 지어낸 사실·숫자가 0인지, 상황/한 일/결과가 맞게 나뉘는지, 같은 경험이 합쳐지는지, 근거 문장이 남는지.
- 결과 예시를 사용자에게 보여 주고 확인받는다.

## 5. 이번 범위 밖

- 지난 분석 자소서·작업실 답변에서 가져오기
- 문항별 경험 추천, 같은 경험 겹침·빈 요건 경고
- 경험을 어느 지원서에 썼는지 표시, 태그로 걸러 보기
- 남은 횟수만 보여 주는 GET

## 남은 위험

- **분류 품질**: 자소서 문장은 상황·행동·결과가 섞여 있다. 모델이 칸을 잘못 나눠도 사용자가 카드에서 고칠 수 있게 한 것이 안전장치다.
- **근거 확인의 엄격함**: 모델이 문장을 조금이라도 바꾸면 후보가 버려진다. 실측에서 버려지는 비율이 높으면 문장 일부(앞 20자) 일치로 완화한다.
- **동시 저장 경쟁**: 개수 검사와 저장 사이의 경쟁은 기존 단일 저장과 같은 수준으로 허용한다(100개 한도는 사업 규칙이 아니라 보호 장치).
