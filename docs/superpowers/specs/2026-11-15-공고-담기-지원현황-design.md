# 지원 현황판 설계: 지원한 곳마다 지금 할 일

- 날짜: 2026-11-15
- 상태: 설계 승인(같은 날 방향 수정 반영), 구현 계획 전

## 1. 왜 하는가

11-01~11-15 운영 기록(관리자·봇 제외 사람 세션 544)을 보면 303세션이 채용 공고 상세로 들어왔고, 다른 화면으로 간 세션은 9개뿐이다. 유입은 chatgpt.com 129가 가장 많다. 이 방문자들은 자소서를 고치러 온 게 아니라 **공고를 보러** 왔다. 이미 쓴 자소서를 진단하는 상품과는 시기가 맞지 않는다.

이 사람들에게 지원한 곳을 한 판에 모으게 하고, **각 지원서가 지금 어느 단계인지에 맞춰 Pre:View만 할 수 있는 다음 할 일을 한 가지씩** 건넨다.

### 1.1 자소설닷컴과의 차이

자소설닷컴은 공고 즐겨찾기(★)를 채용달력에 표시하고, 작성 중인 공고의 마감 하루 전에 알림을 보낸다. 공고별 자소서 문항도 자동으로 붙는다(공식 블로그·공지·앱 소개로 확인, 11-15). 전형 단계 기록 기능은 공식 자료에서 확인하지 못했다.

- **담기 자체는 차별점이 아니다.** 공고 수(우리 149건)와 알림 면에서 자소설닷컴보다 약하다.
- **단계 기록도 단독으로는 차별점이 아니다.** 노션·엑셀로도 할 수 있다. 다만 단계를 알아야 "이 사람은 곧 면접이다"를 알 수 있다. 그래서 단계는 **다음 할 일을 고르는 신호**로 쓴다.
- **차별점은 단계별 다음 할 일이다.** 자소설닷컴은 언제 마감인지 알려주는 일정표다. Pre:View는 지금 글이 괜찮은지(진단), 그 회사에 낸 바로 그 자소서로 면접에서 무엇을 물을지(AI 모의 면접)까지 해준다.

### 1.2 검토했다가 버린 방향

- 메일·카카오 알림톡 알림: 사용자가 기각했다(11-15).
- 로그인 없이 브라우저에만 저장: 가입할 이유가 생기지 않는다.
- 관심 공고 표를 따로 두기: 같은 회사를 두 곳에서 관리하게 되고 단계가 갈린다.
- "지원 현황 관리"를 기능으로 내세우기: 자소설닷컴·노션과 비교되어 진다.

## 2. 성공 기준

- 카드마다 **현재 단계에 맞는 "지금 할 일" 버튼이 하나** 있고, 눌렀을 때 그 지원서의 내용이 채워진 화면으로 바로 간다.
- 로그인한 사용자가 공고 화면에서 '담기'를 누르면, 그 공고가 붙은 지원서가 '관심' 단계로 `/my`에 생긴다.
- 로그인하지 않은 사용자가 '담기'를 누르면 로그인 창이 뜨고, 로그인이 끝나면 추가로 누르지 않아도 담긴다.
- 같은 공고를 다시 담아도 지원서는 하나만 있다.
- `/my`에서 단계를 바꾸고, 단계를 끼워 넣거나 지우고, 불합격을 표시할 수 있다.
- 남의 지원서 단계는 서버가 막는다(404).
- 판독 지표(배포 1~2주 뒤):
  - **"지금 할 일" 클릭 세션 수(단계별)**: 주 지표
  - 그 클릭에서 이어진 분석 요청·면접 세션 시작 수
  - `job-save` 담기 클릭 세션 수, 담기에서 시작한 가입 수

## 3. 사용자 흐름

### 3.1 공고 화면 (`/jobs/:slug`)

- 회사 이름 옆에 '☆ 담기' 버튼을 둔다. 마감된 공고에는 보여주지 않는다.
- 비로그인 사용자가 누르면 로그인 모달을 띄운다. 로그인이 끝나면 자동으로 담는다. 기존 `useSubmitAfterLogin`과 같은 방식으로, 모달을 닫으면 담기도 취소된다.
- 담은 뒤에는 버튼이 '★ 담음 · 지금 할 일 보기'(`/my` 링크)로 바뀐다.
- 담았는지는 로그인 사용자의 `GET /api/projects` 응답 중 `posting_slug`가 이 공고와 같은 지원서가 있는지로 판단한다.
- 버튼 옆 보조 문구는 "지원 현황 관리"가 아니라 "담아두면 단계마다 준비할 것을 알려드려요"로 쓴다(최종 문구는 사용자 검수).

### 3.2 내 페이지 (`/my`) = 지원 현황판

- 지원서 목록을 두 묶음으로 나눈다.
  - **진행 중**: 불합격이 아니고 '최종 합격'도 아닌 것.
  - **결과 나옴**: 최종 합격이거나 불합격인 것.
  - 두 묶음 안의 순서는 지금 쓰는 `sortApplications`(작성 중 → 마감 가까운 순 → 마감 지난 것)를 그대로 쓴다. 지금의 거르기 칸(전체·작성 중·분석 완료)을 '진행 중·결과 나옴'으로 바꾼다.
- **카드의 주인공은 "지금 할 일" 버튼이다.** 카드에서 가장 눈에 띄는 요소로 두고, 버튼 위에 한 줄 이유를 붙인다(예: "서류 합격 · 낸 자소서로 예상 질문을 뽑아 연습해요").
- 회사·직무·마감(D-day)·단계 배지는 보조 정보로 작게 둔다. 배지를 누르면 단계 목록이 펼쳐지고, 고르면 바로 저장한다. 단계 바꾸기는 한 번 누르기로 끝나야 한다.
- 단계 목록 맨 아래에 '+ 단계 추가'와 '불합격 표시/해제'를 둔다.
- 우리 공고판에 없는 회사는 지금처럼 '새 지원서'로 만들면 같은 판에 들어온다.

### 3.3 단계 규칙

- 기본 단계: 관심 → 작성 중 → 서류 제출 → 서류 합격 → 면접 → 최종 합격.
- 불합격은 단계가 아니라 표시(`rejected`)다. 현재 단계와 함께 "면접에서 불합격"처럼 보여준다.
- 사용자는 아무 단계 뒤에나 직접 단계를 끼워 넣을 수 있다(예: 서류 합격 뒤 '과제', 면접 자리에 '1차 면접'·'2차 면접'). 직접 넣은 단계는 지울 수 있고, 기본 단계는 지울 수 없다.
- '최종 합격'은 항상 맨 끝이다. 그 뒤로는 단계를 넣을 수 없다.
- 자동으로 바뀌는 경우는 하나뿐이다. 문항 저장 때 답이 한 글자라도 있고 현재 단계가 '관심'이면 '작성 중'으로 바꾼다. 나머지는 모두 사용자가 직접 바꾼다.

### 3.4 단계별 지금 할 일 (이 기능의 본체)

직접 넣은 단계는 **바로 앞에 있는 기본 단계와 같은 할 일**을 보여준다. 예를 들어 '서류 제출' 뒤의 '인적성'은 서류 제출과 같은 할 일을, '서류 합격' 뒤의 '과제'·'1차 면접'은 면접 연습을 보여준다.

| 단계 | 지금 할 일 버튼 | 가는 곳 | 조건·대체 |
| --- | --- | --- | --- |
| 관심 | "이 회사 문항부터 보기" | 같은 회사의 문항 해설 가이드(`client/content/guides/*.md`의 `company:`와 이름 일치) | 해설 글이 없으면 "자소서 쓰기 시작"(작업실) |
| 작성 중 (+ 서류 묶음 직접 단계) | 답이 있으면 "내기 전에 진단받기", 비어 있으면 "자소서 이어 쓰기" | 진단은 그 지원서로 분석 흐름, 쓰기는 작업실 | 이미 성공한 분석이 있으면 "진단 리포트 보기" |
| 서류 제출 | "결과 기다리는 동안 면접 미리 준비" | AI 모의 면접 시작 화면, 이 지원서를 미리 골라 둠 | 지원서에 답도 분석도 없으면 "낸 자소서 붙여 넣기"(작업실) |
| 서류 합격·면접 (+ 면접 묶음 직접 단계) | **"낸 자소서로 면접 연습"** | AI 모의 면접 시작 화면, 이 지원서를 미리 골라 둠 | 같은 회사 면접 후기 가이드가 있으면 보조 링크 "이 회사 면접 후기" |
| 최종 합격 | 없음(축하 한 줄) | — | — |
| 불합격 표시 | 없음 | — | 패턴 안내는 범위 밖(9절) |

- 회사 이름은 공백을 없애고 대소문자를 무시해 정확히 같을 때만 일치로 본다. 애매하면 링크를 숨긴다.
- AI 모의 면접 시작 화면(`InterviewPracticeList`)은 이미 지원서를 골라 자소서를 불러올 수 있다. 여기에 `?application=<id>` 쿼리를 받아 처음부터 그 지원서를 골라 두게 하는 것만 더한다. 결제·크레딧·면접 진행 규칙은 바꾸지 않는다.
- 지금 `/`와 `/my`에 아무에게나 뜨는 면접 팝업은 이 설계 범위에서 건드리지 않는다. 판독 뒤 따로 정한다.

## 4. 데이터

`projects` 테이블에 칸 3개를 추가한다(`prisma/schema.prisma`의 `Project`).

| 칸(DB / Prisma) | 타입 | 기본값 | 뜻 |
| --- | --- | --- | --- |
| `stage` / `stage` | `VARCHAR(40)` | `'writing'` | 현재 단계 키 |
| `stage_steps` / `stageSteps` | `JSONB` NULL | NULL | 이 지원서의 단계 목록. NULL이면 기본 목록 |
| `rejected` / `rejected` | `BOOLEAN` | `false` | 불합격 표시 |

- 기본 단계 키: `interest`, `writing`, `submitted`, `doc_passed`, `interview`, `offer`. 화면 이름표는 클라이언트 상수가 정한다.
- 직접 넣은 단계 키는 클라이언트가 만든다. `c_` 뒤에 영문 소문자·숫자 8자를 붙인다(예: `c_k3m9x2ab`).
- `stageSteps` 형식: `[{ "key": "interest" }, …, { "key": "c_k3m9x2ab", "label": "과제" }, …, { "key": "offer" }]`. 기본 단계에는 `label`이 없고, 직접 넣은 단계에는 `label`이 반드시 있다.
- 마이그레이션은 칸만 추가한다. 기존 지원서는 기본값에 따라 '작성 중'·기본 목록·불합격 아님 상태가 된다. 기존 데이터를 바꾸거나 지우지 않는다.
- 운영 DB 적용은 사용자 승인을 받은 뒤에 한다.

## 5. 서버 API

새 함수와 새 경로는 없다. 기존 `api/projects.js`와 `api/projects/[projectId]/index.js`를 넓힌다. Vercel 함수 수(12)와 `vite.config.ts` 개발 매핑은 그대로다.

검사 로직은 `lib/application-drafts.js`에 함께 둔다(`normalizeProjectCreate`·`normalizeProjectMeta` 옆에 `normalizeStageSteps` 추가).

### 5.1 담기: `POST /api/projects`

- 받는 키에 `stage`를 더한다. `"interest"`만 허용하고, 없으면 기본값(`writing`)을 쓴다.
- `stage === "interest"`이고 `postingSlug`가 있으면, 같은 사용자에게 같은 `postingSlug` 지원서가 이미 있는지 먼저 본다.
  - 있으면 새로 만들지 않고 `200 { id, existing: true }`를 돌려준다.
  - 없으면 지금처럼 만들고 `201 { id }`를 돌려준다.
- 회사·마감일·직무는 클라이언트가 공고 상수(`client/src/constants/jobPostings.ts`)에서 채워 보낸다. 사용자 본인의 데이터라 서버가 다시 확인하지 않는다.
- 유니크 제약은 걸지 않는다. 기존 "내 경험으로 초안 쓰기"로 같은 slug 지원서가 이미 여러 개 있을 수 있다. 동시에 두 번 누르는 경쟁은 클라이언트에서 버튼을 잠가 막는다.
- 지원서 상한(200)은 담기에도 똑같이 적용한다.

### 5.2 단계 수정: `PATCH /api/projects/:id`

- `normalizeProjectMeta`가 받는 키에 `stage`, `stageSteps`, `rejected`를 더한다.
- 검사 규칙(어기면 `400 INVALID_REQUEST`):
  - `rejected`는 boolean이어야 한다.
  - `stageSteps`는 배열이어야 한다. `null`은 받지 않는다. Prisma에서 JSON 칸에 null을 쓰려면 `Prisma.DbNull`이 필요한데 저장소에 그렇게 쓴 곳이 없다. 기본 목록으로 되돌릴 때도 클라이언트가 기본 6단계 배열을 보낸다.
  - 6~12개다(기본 6개가 반드시 들어가므로 최소 6개). 기본 6개 키가 원래 순서대로 모두 들어 있어야 하고, 마지막은 `offer`여야 하며, 키가 서로 달라야 한다. 직접 넣은 단계 키는 `^c_[a-z0-9]{8}$` 형식이고, `label`은 다듬은 뒤 1~20자여야 한다.
  - `stage`는 저장 후 단계 목록에 있는 키여야 한다. 이번에 보낸 `stageSteps`가 있으면 그것을, 없으면 저장된 값을 기준으로 본다. 현재 단계를 지우는 `stageSteps`도 이 규칙으로 거절된다.
- 소유권 확인은 지금처럼 `where: { id, userId }`로 하고, 없으면 404를 돌려준다.
- 응답에 `stage`, `stage_steps`, `rejected`를 더한다.

### 5.3 자동 넘김: `PUT /api/projects/:id`

문항을 저장할 때, 답이 하나라도 비어 있지 않고 현재 `stage`가 `interest`이면 같은 트랜잭션 안에서 `writing`으로 바꾼다. 분석 뒤 잠금(409 `APPLICATION_LOCKED`)의 의미는 그대로 둔다.

### 5.4 목록: `GET /api/projects`

SQL 선택 칸에 `p.stage`, `p.stage_steps`, `p.rejected`, `p.posting_slug`를 더하고, 응답에 `stage`, `stage_steps`, `rejected`, `posting_slug`를 내보낸다. 기존 필드 이름은 바꾸지 않는다. "지금 할 일" 판단에 필요한 `answered_count`·`latest_analysis_id`·`latest_status`는 이미 응답에 있다.

- 회사별 가이드 정보는 가이드 frontmatter의 `company`(파서 `shared/guideFrontmatter`, 목록 `client/src/lib/guides.ts`의 `GUIDES`)에서 온다. 단, `GUIDES`는 글 본문을 `?raw` + `eager`로 통째로 싣는다. 그래서 `/my`에서 그대로 import하면 모든 가이드 본문이 번들에 들어간다. 구현 때는 회사·슬러그·종류(문항 해설/면접 후기)만 담은 가벼운 색인을 따로 만들거나 기존 `guideSummaries.ts` 같은 요약 경로를 쓴다. 정확한 방식은 구현 계획에서 정한다.
- 클릭 기록은 `content_cta_click`에 남긴다. 담기는 `job-save:<slug>`, 지금 할 일은 `next-action:<단계 키 또는 묶음>:<행동>`(예: `next-action:doc_passed:interview`)이다.
- 스타일은 기존 Tailwind·Radix 패턴을 따르고 새 라이브러리는 들이지 않는다. 버튼 강조는 기존 취향(흰 버튼·톤 차이)을 따르고, 그라데이션이나 떠 있는 배지는 쓰지 않는다.

## 7. 오류 처리

- 담기 실패(네트워크·500): 버튼을 원래대로 돌리고 "담지 못했어요. 다시 눌러 주세요"를 보여준다.
- 지원서 상한(409 `PROJECT_LIMIT_REACHED`): 기존 문구를 재사용한다.
- 단계 저장 실패: 배지와 "지금 할 일"을 이전 단계 기준으로 되돌리고 짧게 안내한다(낙관적 갱신 후 롤백).
- 로그인 창을 닫았을 때: 담지 않는다.
- `?application=<id>`가 내 지원서 목록에 없을 때: 아무것도 미리 고르지 않고 평소 화면을 보여준다.

## 10. 남은 위험

- 자소설닷컴·노션·엑셀로 이미 관리하는 사람은 두 곳에 적기 싫어할 수 있다. 처음에는 ChatGPT·검색으로 우리 공고에 처음 들어온 사람의 첫 담기에 기대고, "지금 할 일" 클릭 수로 판단한다.
- 사용자가 단계를 직접 바꾸지 않으면 "지금 할 일"이 옛 단계에 머문다. 서류 제출 단계에 "결과 나왔어요?" 같은 가벼운 단계 바꾸기 유도를 붙일지는 판독 뒤 정한다.
- 가이드 회사 이름과 지원서 회사 이름이 다르게 적히면(예: "CJ그룹"과 "CJ제일제당") 링크가 안 뜬다. 틀린 연결보다 안 뜨는 쪽을 택했다.
- `/my`가 '내 지원서'에서 현황판으로 바뀌면서 기존 사용자가 낯설어할 수 있다. 기존 카드 정보는 유지한다.
- 담은 순간의 회사명·마감일을 복사하므로, 나중에 공고 상수가 고쳐져도 이미 담은 지원서에는 반영되지 않는다.
