# 성장 운영 고리 설계

- 날짜: 2026-10-19
- 상태: 승인된 방향(0~2단계 완료), 3단계 시범 운영 전
- 근거: Codex Phase 1 진단 보고서(저장소 읽기 전용) + 0단계 운영 확인(운영 DB·프로덕션 번들·예약 작업·대기열 저장소, 모두 읽기 전용)

> 이 문서는 **공개 저장소**에 있다. 가입자·결제·퍼널 숫자는 쓰지 않는다. 숫자는 비공개 `.agents/growth/metrics.md` 에만 둔다.

## 1. 목표

Pre:View의 **실제 가입자 증가**. 에이전트를 만드는 것 자체는 목표가 아니다.

- 기준 지표: **주간 신규 가입자 수**(KST 월~일, 관리자 제외). 정의는 `.agents/growth/metrics.md`.
- 이 설계가 성공했다는 뜻:
  1. 주간 판독이 매주 실제로 한 번 돈다.
  2. 판독에서 고른 실험 하나가 기존 루틴이나 제품 변경 하나에 실제로 반영된다.
  3. 8주 뒤 "최근 4주 가입 합계"를 지금 기준선과 비교할 수 있다.

## 2. 배경 — 이미 있는 것과 빠진 것

**이미 있는 것**

- 콘텐츠 생산은 이미 예약 작업으로 돌고 있다(아래 4절 표). 초안까지 자동이고, 발행·머지는 사람이 한다.
- 방문·작성 시작·가입·분석 완료·결제를 세는 자체 집계가 있다(`lib/admin-handlers/behavior.js`, 관리자 "사용 행동" 탭).
- 블로그 링크에는 `utm_source=naverblog` 규칙이 있다(`.agents/blog-job-posts/style.md`).

**빠진 것**

- 어느 예약 작업도 **가입을 기준으로 자기 결과를 판정하지 않는다.** 성과를 재는 작업은 스레드 주간 회고 하나뿐이고, 기준은 팔로워다.
- 채널 성과를 가입과 잇는 주기적 판독이 없다. 0단계 확인에서 채널마다 가입으로 이어지는 정도가 크게 다르고, 사이트 안 한 단계(분석 폼 열람 → 작성 시작)에서 가장 많이 샌다는 것이 처음 드러났다.
- 스레드 링크의 utm 규칙 문서가 없다.

## 3. 결정 — 새 에이전트 대신 "주 1회 고리" 하나

상주 에이전트 네 개를 만들지 않는다. 콘텐츠는 기존 예약 작업이 맡고 있으므로, 빠진 고리 하나만 더한다.

> 주간 신규 가입으로 지난주를 판정 → 실험 대장에서 다음 행동 하나를 고름 → 기존 루틴이나 제품 작업에 넘김

**고른 이유:** 새 에이전트는 기존 채널 지침과 규칙을 복제해 정본을 둘로 만든다. 지금 병목은 생산량이 아니라 **판정 기준이 없다는 것**이다.
**포기한 것:** 채널별 자율 최적화. 방문이 적어 채널마다 따로 판단할 만큼의 숫자가 아직 없다.

## 4. 역할과 경계

역할은 사람·세션이 쓰는 **모자**이지, 따로 상주하는 프로그램이 아니다.

| 역할 | 하는 일 | 입력 | 출력 | 하지 않는 일 | 사람 승인 |
| --- | --- | --- | --- | --- | --- |
| 전략 | 주간 판독을 보고 다음 실험 하나를 고른다 | `metrics.md`, `experiments.md`, 스레드 주간 회고 결과, `.agents/product-marketing.md`, 경쟁사 요약 | `experiments.md` 의 실험 선택·판정 | 원고·코드 작성 | 실험 선택, 가격·포지셔닝 변경 |
| 분석 | 숫자를 뽑고 정의대로 읽는다 | 운영 DB(읽기 전용), 관리자 "사용 행동" 탭 | 주간 판독 파일 `.agents/growth/weekly/YYYY-MM-DD.md` | DB 쓰기, 새 추적 수집, 게시 | 새 데이터 수집, 개인정보 접근 확대 |

| 엔지니어링 | 승인된 측정·제품 변경만 구현한다 | 실험 대장의 요청, `CLAUDE.md` | 검증된 변경(리뷰 가능한 diff/PR) | 요청 없는 기능, 배포 | 배포, 권한·결제·DB 변경 |

## 5. 주간 고리 절차

- 언제: **매주 월요일 22:00 KST** — 직전 주(월~일)가 끝난 뒤, 월요일 21시 예약 작업들이 끝난 다음. 아침에는 노트북을 켤 수 없는 운영 조건에 맞춘 시각이다.
- 누가: 3단계(시범)에서는 사람이 대화 세션으로, 4단계부터는 예약 작업 하나로.

1. **숫자 뽑기(분석):** `metrics.md` 6절 방법으로 지난주와 최근 4주 숫자를 읽는다. 읽기 전용.
2. **판독(분석):** 기준 지표 → 단계별 변화 → 유입원(방문자·작성 시작까지만) 순서로 `.agents/growth/weekly/YYYY-MM-DD.md` 에 쓴다. 스레드 주간 회고 결과는 인용만 한다.
3. **판정(전략):** 진행 중 실험이 있으면 비교 구간이 찼는지 보고 유지 / 되돌림 / 판단 보류 중 하나로 판정한다. 없으면 후보 중 하나를 추천한다.
4. **넘기기:** 고른 행동을 실행 경로에 넘긴다. 콘텐츠면 해당 채널 지침, 제품이면 엔지니어링 작업.
5. **사람 확인:** 실험 시작과 판정은 사용자가 승인한다.

## 7. 모델에 묶이지 않는 원칙

- 역할 지침은 `.agents/` 아래 **평범한 마크다운**으로만 둔다. 특정 도구 전용 위치(예: `.claude/agents/`)에 역할 정의를 만들지 않는다.
- 지침에는 모델 이름이 아니라 **필요한 능력 등급**만 적는다.
  - 전략: 추론이 강한 상위 등급. 주 1회라 비용이 작다.
  - 분석: 숫자는 스크립트·집계 코드가 계산하고, 모델은 읽고 해석만 → 중간 등급.
  - 콘텐츠: 지금 운영 중인 설정을 유지한다. 바꾸면 발행본에서 학습한 말투가 흔들릴 수 있다.
  - 엔지니어링: 저장소 규칙(`CLAUDE.md`)을 따르는 코딩 에이전트면 어느 것이든.
- `AGENTS.md` 는 `CLAUDE.md` 를 가리키는 심링크(Git 모드 120000)라 도구가 달라도 같은 규칙을 읽는다. 로컬 `core.symlinks=false` 체크아웃에서는 글자 파일로 풀릴 수 있다.

## 8. 만들지 않는 것

- 상주 에이전트, 채널별 독립 에이전트
- 새 방문 수집기·새 API 엔드포인트(Vercel Hobby 12함수 제한, 자체 집계가 이미 있음)
- 새 발행 경로(스레드는 기존 대기열, 블로그·가이드는 사람이 발행·머지)
- 채널 지침의 복제본
- 사이트 방문자에 대한 A/B 분할(방문이 적어 통계적으로 의미 없음 — 전후 비교로 대신)

**4단계로 넘어가는 기준:** 시범 2회가 모두 실험 선택이나 판정 같은 결정으로 이어졌고, 같은 절차를 반복할 만하다고 사용자가 판단할 때. 결정으로 이어지지 않으면 자동화하지 않는다.

## 10. 위험

- **숫자가 작다.** 주 단위 가입은 우연에 크게 흔들린다 → 판정은 4주 합계와 전후 2주 비교로만 한다.
- **채널 귀속이 부정확하다.** 탭 세션 ID, referrer를 숨기는 인앱 브라우저, 부풀려진 유입원별 가입 칸 → 채널 비교는 방문자·작성 시작까지만 한다.
- **비공개 정보 유출.** 공개 저장소다 → 숫자는 `.agents/growth/` 에만 두고, 커밋 전에 숫자 포함 여부를 확인한다.
- **판독만 하고 실행이 없을 수 있다.** → 고리마다 "넘긴 행동 하나"가 없으면 그 주 판독은 실패로 본다.
