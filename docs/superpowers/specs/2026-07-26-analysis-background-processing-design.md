# 분석 백그라운드 처리 설계

## 목적

Gemini 분석이 현재 45초의 애플리케이션 타임아웃을 넘을 때 사용자에게 504 오류가 보이는 문제를 해결한다. 분석은 로그인 사용자만 사용할 수 있고, 기존의 이용권 예약·idempotency·소유권 검증·분석 중단 스위치 보안 경계를 유지한다.

사용자 경험은 다음과 같다.

1. 분석 시작 직후 `분석 중` 화면으로 이동한다.
2. 화면은 분석 상태를 주기적으로 확인한다.
3. 성공하면 리포트를 자동으로 연다.
4. 실패하면 이용권을 되돌린 뒤 안전한 오류 안내와 새 분석 시작 방법을 보여 준다.

## 범위와 비범위

포함:

- Vercel의 `waitUntil`을 이용한 같은 요청 수명 안의 백그라운드 분석 처리
- `AnalysisRequest` 상태 조회 API와 진행 화면
- 100초 모델 호출 제한, 120초 함수 제한, 멈춘 요청의 안전한 종료
- 보안·비용 정합성 회귀 테스트와 스테이징 재검증

포함하지 않음:

- 외부 작업 대기열 서비스, 신규 외부 계정 또는 신규 비밀값
- Gemini 이외의 모델로 자동 재호출하거나 자동 폴백하는 기능
- 결제/Premium 기능 재도입
- 운영 환경 배포

## 전제 조건

- Vercel 프로젝트의 Fluid Compute가 활성화되어 있어야 한다.
- `api/analyze.js`의 함수 최대 실행 시간을 120초로 설정할 수 있어야 한다.
- 현재 배포의 보안 브랜치와 스테이징 Supabase만 검증 대상이다.

`waitUntil` 작업도 함수 최대 실행 시간 안에서만 실행된다. 따라서 이는 영구 작업 대기열이 아니라, 베타에 필요한 지연 흡수 방식이다. 120초를 넘거나 플랫폼 작업이 중단되면 요청은 안전하게 실패로 닫히며 자동 모델 재호출을 하지 않는다.

## 아키텍처와 데이터 흐름

### 분석 접수

`POST /api/analyze`는 현재와 같이 Bearer 토큰을 검증하고 `token.sub`만 사용자 식별자로 사용한다. 서버는 입력 검증, 15분 3회 제한, `analysisEnabled`, idempotency key를 확인한 뒤 하나의 DB 트랜잭션에서 다음을 생성한다.

- `Project`
- `Analysis` (`PENDING`)
- `AnalysisReservation` (`PENDING`)
- `AnalysisRequest` (`PENDING`)

접수가 끝나면 응답은 리포트 원문 없이 `202 Accepted`와 `analysis_request_id`, `analysis_id`, 상태 조회에 필요한 식별자만 반환한다. `waitUntil`에 등록한 작업은 `AnalysisRequest`를 원자적으로 `CALLING`으로 바꾼 뒤 Gemini를 한 번 호출한다.

### 결과 처리

백그라운드 작업은 기존의 결과 저장 단계를 재사용한다.

1. 유효한 Gemini 결과를 임시 저장해 `PERSISTENCE_PENDING`으로 만든다.
2. 하나의 DB 트랜잭션으로 `Analysis` 결과·토큰 사용량을 저장하고, 예약을 `CONSUMED`, 요청을 `SUCCEEDED`로 바꾼다.
3. 성공 응답에는 리포트 원문을 포함하지 않고 분석 ID만 제공한다. 리포트는 기존 소유권 보호 상세 API에서만 읽는다.

저장 트랜잭션 직전에 실패하면 `PERSISTENCE_PENDING` 상태의 안전 복구를 시도한다. 결과가 완전히 저장되기 전에는 이용권을 소비 처리하지 않는다.

### 상태 조회와 화면

새 상태 조회 API는 인증을 요구하고, 요청 ID와 `token.sub`를 함께 조건으로 사용한다. 타 사용자 또는 존재하지 않는 요청은 모두 `404`를 반환한다. 응답은 아래의 비민감 정보만 포함한다.

- `PENDING`, `CALLING`, `PERSISTENCE_PENDING`, `SUCCEEDED`, `FAILED`
- 성공 시 `analysis_id`
- 실패 시 일반화된 오류 코드

클라이언트는 `POST /api/analyze`의 202 응답 뒤 `/analysis-pending?requestId=<request-id>`으로 이동한다. 진행 화면은 3초 간격으로 상태 API를 호출한다. `SUCCEEDED`이면 `/report-new?analysisId=<analysis-id>`으로 이동하고, `FAILED`이면 설명 없이 재시도 안내를 표시한다. 새로고침과 화면 이탈은 서버 작업을 취소하지 않으며, 같은 진행 URL을 다시 열면 조회를 재개한다.

## 시간 초과·중복·비용 처리

- 모델 네트워크 호출 제한: 100초
- Vercel 함수 전체 제한: 120초
- 진행 화면 브라우저 요청 제한: 상태 조회별 짧은 기본 제한만 적용한다. 모델 결과를 기다리는 단일 브라우저 요청은 없다.
- 동일 idempotency key는 기존 요청 상태를 반환하며 Gemini를 다시 호출하지 않는다.
- DB의 `PENDING → CALLING` 조건부 갱신은 중복 클릭·새로고침·동시 요청에서 하나의 작업만 Gemini를 호출하게 한다.
- `CALLING` 또는 `PENDING` 상태가 허용 시간을 초과하면 상태 조회 경로가 원자적으로 `FAILED` 처리하고 분석 예약을 `CANCELLED` 처리한다.
- 429/500/503 또는 모델 타임아웃 뒤에는 자동 모델 재시도를 하지 않는다. 공급자가 이미 처리했을 수 있어 비용 중복 위험이 있기 때문이다.
- 사용자가 다시 시도할 때만 새 idempotency key를 발급한다.

## 보안과 운영

- 진행 상태·리포트·피드백의 소유권은 서버에서만 검증한다. 브라우저가 보낸 사용자 ID·역할·분석 결과·토큰 사용량은 신뢰하지 않는다.
- `analysisEnabled=false`이면 접수 단계에서 `503 ANALYSIS_DISABLED`로 실패 닫힘한다. 백그라운드 작업을 등록하지 않는다.
- 응답과 로그에는 Gemini 키, 액세스 토큰, 자소서 원문, 리포트 원문, 이메일, 공급자 원문 오류를 기록하지 않는다. 오류 응답은 일반화된 코드와 request ID만 반환한다.
- 기존 RLS 기본 거부와 Prisma 서버 전용 데이터 경계는 변경하지 않는다.
- Vercel 환경 설정에서 Fluid Compute를 확인하고, 함수 최대 시간은 저장소 설정으로 명시한다.

## 검증 기준

자동 테스트는 다음을 포함한다.

- 비로그인 상태 조회는 401, 타 사용자 상태 조회는 404
- 202 접수 뒤 상태 전이와 성공 시 분석 ID 반환
- 동일 idempotency key·동시 접수에서 Gemini 호출이 한 번임
- 모델 타임아웃/공급자 오류/작업 만료에서 `FAILED`와 예약 취소
- `PERSISTENCE_PENDING` 복구의 결과·이용권 정합성
- kill switch, rate-limit, 기존 프로젝트·리포트 소유권 회귀

스테이징에서는 A/B 계정과 비민감 테스트 자소서로 다음을 확인한다.

1. A와 B 각각 `접수 → 진행 화면 → 자동 리포트 열기`를 성공한다.
2. B가 A의 진행 요청 ID 또는 리포트 ID를 사용하면 404만 받는다.
3. 모델을 주입한 자동 통합 테스트에서 동시 10건을 실행해 한 요청당 프로젝트·분석·예약·모델 호출이 각각 한 번만 생성되는지 확인한다. 실제 스테이징에서는 사용자당 15분 3회 제한을 유지하고, 초과 요청이 429로 차단되는지를 확인한다.
4. kill switch, 시간 초과, 공급자 실패 시 결과·예약·감사 로그가 서로 일관된다.

완료 후 스테이징 보안감사 보고서의 P1-01, P1-02 및 GO/NO-GO 판정을 실제 증적에 따라 갱신한다.

## 출시 판단

이 설계만으로 출시 가능 판정을 내리지 않는다. 위 자동 테스트와 실제 스테이징 A/B·동시성 검증을 통과한 후에만 P1 차단 항목의 해제 여부를 판단한다.
