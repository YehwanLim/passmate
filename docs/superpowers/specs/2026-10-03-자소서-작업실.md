> 상태: **초안 — 사용자 검토 대기**. 승인 전에는 구현하지 않는다.
> 10-03 결정 반영: `/my`를 **내 지원서 / 내 경험** 두 탭으로 나눈다. 내 지원서는 기존 Project 확장, 공고 보드는 파일 기반.

## 1. 왜 바꾸나

- **지금 Pre:View는 "입력 → 리포트 1장"으로 끝나는 일회성 도구다.**
  - 회사·직무·문항·자소서를 매번 직접 넣어야 한다.
  - 한 번 쓰면 다시 올 이유가 없다.
  - 10-02 실측: 외부 사용자 분석 09-04 이후 0건, 실결제 0건.
- **경쟁사는 셋 중 하나다.**
  - 대신 써 주는 AI: 티오·하이잡·캐치·사람인
  - 점수를 매기는 AI: 합격닷컴·스캐너
  - 문장을 고쳐 주는 곳: 무아레쥬메·크몽
- **비어 있는 자리**: "무엇을, 어느 문항에, 어떤 각도로 쓸지"를 정해 주고, 글은 본인이 쓰게 한 뒤, 채용 담당자 눈으로 읽어 주는 곳이 없다.
  - 창업자가 커피챗 200회에서 해 온 일이다: 경험 라이브러리, 재탕 판단법, 4단 공식, "면접은 컨셉이다".

## 2. 확정된 원칙 (사용자 결정, 10-03)

1. **경험 관리 + 공고 연결 + 작성 + 진단**을 한 흐름으로 만든다. 자소설닷컴보다 자소서 작성에 더 특화한다.
2. **AI는 뼈대까지만.** 경험 배치, 4단 뼈대(불릿), 첫 문장 방향까지만 준다. 문장 생성·대필은 하지 않는다.
3. **도구는 무료, 진단은 유료.**
   - 무료: 공고 보드, 에디터, 경험 금고, 출제 의도
   - 하루 몇 회 무료: 가벼운 AI(경험 추출, 배치 추천)
   - 이용권 유지: 진단 리포트, 기업 분석. 가격표는 바꾸지 않는다.
4. **의도 vs 인상**을 진단에 넣는다(P5).
5. **창업자가 반복해서 손대는 운영 작업은 넣지 않는다.** 이미 하고 있는 블로그 공고 정리만 재활용한다.
6. **Vercel 무료 플랜을 유지한다.** 함수 12개 한도 안에서 기존 라우터에 얹거나 합친다.

## 3. 전체 흐름과 단계

```
공고 고르기(보드·링크) → 문항이 깔린 지원서 → 문항마다 출제 의도·경험 추천·4단 뼈대
→ 에디터에서 내가 작성(자동 저장) → (유료) 진단 → 지적받은 문장을 옆에 두고 고쳐 쓰기
→ 다음 공고에서 경험 재사용, 마감순 현황판
```

| 단계 | 내용 | 무료/유료 | 이 문서의 상세도 |
|---|---|---|---|
| P1 | **작업실 + 내 경험 직접 입력**: 지원서별 문항 에디터, 자동 저장, 마감순 현황판, 지원서에서 바로 진단, 경험 카드(한 줄 이름·상황·행동·결과·키워드) | 무료(진단만 이용권) | **상세** (구현 계획 있음) |
| P2 | **경험 추천**: 지원서 문항마다 "어떤 경험을 쓸지" 1~2개와 이유·쓸 각도(불릿), 겹침·빈칸 경고 | 무료 하루 N회 | **상세** |
| P3 | **공고 보드**: 큐레이션 공고 목록·상세(SEO), "이 공고로 시작" | 무료 | **상세** |
| P4 | 경험 자동 추출(붙여넣은 자소서·지난 분석에서) + 4단 뼈대 | 무료 하루 N회 | 개요 |
| P5 | 진단 강화: 의도 vs 인상, 에디터 옆 진단, 기업 분석 소재 연결 | 유료 | 개요 |

하지 않는 것: 고친 글 다시 진단해 전후 비교(10-03 기각), 문장 생성·대필.

P0(별건): `/analyze` 빈 화면 수정(10-02 작업분, 미커밋)과 "1분" 문구 실측 후 수정. 사용자가 배포를 승인할 때 진행한다.

## 4. P1 작업실 — 상세

> **구현 계획 반영(10-03, `docs/superpowers/plans/2026-10-03-내-지원서-작업실.md`)** — 아래 4-3·4-4와 달라진 점:
> 1. 함수 파일을 합치지 않고 기존 `api/projects/[projectId]/index.js`에 PATCH(메타)·PUT(문항 저장)을 얹는다. 함수 수 12 유지, `vercel.json` 미변경.
> 2. 남의 지원서로 보낸 진단은 `PROJECT_NOT_FOUND` 대신 기존 공고 연결과 같은 404 `NOT_FOUND`.
> 3. 기존 지원서 미리채움은 서버가 아니라 클라이언트가 기존 `parseAnalysisSections`로 한다.

### 4-1. 사용자에게 보이는 동작

- **`/my`는 두 탭으로 나뉜다(사용자 결정 10-03): 내 지원서 / 내 경험.**
  - P1에서 "내 지원서"와 "내 경험"(직접 입력) 두 탭을 함께 연다. 경험 자동 추출은 P4.
  - **대시보드 배치(10-03 사용자 요청)**: 데스크톱은 왼쪽에 계정·남은 이용권(자소서 진단·기업 분석 N회, 무료 1회 남음 안내, "이용권 사기"·"자세히 보기"), 오른쪽에 두 탭. 폰은 이용권 칸이 위. 누적 통계·아바타는 넣지 않는다.
- **내 지원서 탭 = 현황판** (기존 "내 지원서" 목록을 바꿈)
  - 지원서를 **마감 임박순**으로 정렬한다. 마감이 없으면 최근 수정순으로 뒤에 둔다.
  - 카드마다 회사·직무, D-day, 문항 작성 진행(예: 3/5 작성), 진단 횟수를 보여 준다.
  - "새 지원서" 버튼: 회사·직무·마감(선택)·문항(1~5개, 문항 원문과 글자 수 제한)을 입력해 만든다.
- **`/my/:projectId` 작업 화면** (기존 분석 목록 화면을 확장)
  - 위: 회사·직무·마감(수정 가능)
  - 가운데: 문항 탭 + 에디터(textarea). 글자 수는 공백 포함/제외를 함께 보여 주고, 문항 제한을 넘으면 경고한다.
  - **자동 저장**: 입력이 멈추고 1.5초 뒤 저장, "저장됨 · 방금" 표시. 저장 실패 시 다시 시도 안내를 띄우고, 작성 내용은 브라우저에도 임시 보관한다.
  - "이 지원서로 진단받기" 버튼은 현재 문항과 답변으로 기존 분석을 시작한다. 크레딧·대기 화면·리포트는 그대로다.
  - 아래: 이 지원서의 지난 진단 목록(기존 MyAnalyses 내용)
- **기존 빠른 경로는 유지한다.** 랜딩 CTA → `/analyze` → 리포트. 이렇게 만든 분석도 지원서로 남으니 나중에 작업 화면에서 이어 쓸 수 있다.
- **기존 지원서**(문항 데이터 없이 분석 1건만 있는 것): 작업 화면을 처음 열면 최신 분석의 문항·답변으로 에디터를 미리 채운다. 저장하기 전에는 DB에 쓰지 않는다.

### 4-2. 데이터 모델

`Project`를 "지원서" 그릇으로 쓴다. 지금은 분석 1건마다 Project가 하나씩 생긴다(`lib/analysis-request-lifecycle.js`). 앞으로는 지원서 하나에 진단 여러 건이 쌓인다.

```prisma
model Project {
  // 기존 필드 유지 (id, userId, title, company, jobKeyword, createdAt, updatedAt)
  deadline    DateTime? @db.Timestamptz                       // 접수 마감
  postingSlug String?   @map("posting_slug") @db.VarChar(120) // P3 공고 보드에서 시작했으면 그 공고
  questions   ApplicationQuestion[]
}

model ApplicationQuestion {
  id        String   @id @default(uuid()) @db.Uuid
  projectId String   @map("project_id") @db.Uuid
  position  Int                                   // 1~5
  prompt    String   @db.Text                     // 문항 원문
  charLimit Int?     @map("char_limit")           // 글자 수 제한(없을 수 있음)
  answer    String   @default("") @db.Text        // 작성 중인 답변
  updatedAt DateTime @default(now()) @updatedAt @map("updated_at") @db.Timestamptz

  project Project @relation(fields: [projectId], references: [id], onDelete: Cascade)

  @@unique([projectId, position])
  @@map("application_questions")
}
```

- 문항 수와 글자 수 한도는 분석 입력 규칙(`lib/resume-analysis.js`: 문항 최대 5개, 답변 길이 제한)과 같게 둔다. 그래야 "진단받기"가 항상 통과한다.
- User 삭제 → Project Cascade → 문항 Cascade이므로 계정 삭제 purge 경로가 그대로 덮는다(테스트로 확인).
- 마이그레이션은 컬럼·테이블 **추가만** 한다. 적용은 사용자가 환경을 지목할 때만 한다.

### 4-3. 분석과 지원서 연결 (비즈니스 규칙 변경 — 신중히)

- `/api/analyze` 요청 본문에 선택 필드 `projectId`(uuid)를 추가한다.
  - `lib/resume-analysis.js` allowedKeys에 추가하고 형식을 검증한다.
  - **요청 해시에 포함한다.** 같은 자소서라도 다른 지원서로 보낸 요청은 별개 요청이다.
  - `projectId`가 있으면 lifecycle 트랜잭션 안에서 `project.findFirst({ id, userId })`로 **소유권을 확인**한다.
    - 없거나 남의 것이면 404 `PROJECT_NOT_FOUND`(새 에러 코드, 클라이언트 파서에 추가).
    - 있으면 새 Project를 만들지 않고 그 지원서에 분석을 붙인다.
  - `projectId`가 없으면 지금과 똑같이 새 Project를 만든다(빠른 경로).
- **바꾸지 않는 것**: 상태 집합, 멱등성 키 유니크, 크레딧 선예약·확정·취소, 처리량 제한, 응답 필드명(`analysis_id`, `analysis_request_id`, `project_id`).
- 진단 후 지원서 제목·회사·직무를 분석 입력으로 덮어쓰지 않는다. 지원서가 원본이다.

### 4-4. API — 함수 12개 한도 안에서

- 지금 함수는 12개로 꽉 찼다.
- `api/projects/[projectId]/index.js`와 `api/projects/[projectId]/analyses.js`를 **하나의 라우터로 합친다**. 그러면 함수가 11개가 되고 한 자리가 비지만, P1에서는 쓰지 않고 남겨 둔다.
- 합친 파일 이름과 방식은 계정·관리자 라우터와 같은 패턴(`[...route]` + `vercel.json` rewrite로 `route` 쿼리 전달)으로 한다. 정확한 파일 구조는 구현 계획에서 정한다.

| 메서드·경로 | 동작 | 권한 |
|---|---|---|
| `GET /api/projects` | 현황판 목록. 기존 응답 + `deadline`·`question_count`·`answered_count`·`updated_at` | 로그인(활성 사용자) |
| `POST /api/projects` | 새 지원서(회사·직무·마감·postingSlug·문항 배열) → 201 + id | 로그인 |
| `GET /api/projects/:id` | 지원서 상세 + 문항 목록(없으면 최신 분석에서 만든 미리채움, `seeded: true` 표시) | 소유자만, 아니면 404 |
| `PATCH /api/projects/:id` | 회사·직무·마감·제목 수정 | 소유자만 |
| `PUT /api/projects/:id/questions` | 문항 전체 저장(자동 저장). 본문에 `baseUpdatedAt`, 서버 값이 더 새로우면 409 `STALE_DRAFT` | 소유자만 |
| `DELETE /api/projects/:id` | 기존 그대로 | 소유자만 |
| `GET /api/projects/:id/analyses` | 기존 그대로 | 소유자만 |

- 모든 핸들러는 `withApiHandler`/`ApiError`, `requireActiveApplicationUser`, `lib/sanitize.js`를 쓴다.
- 문항 저장은 짧은 주기로 반복되므로 감사 로그를 남기지 않는다. 본문은 로그 금지 대상이다.
- 남의 지원서는 존재 여부를 숨기려고 403 대신 404로 응답한다(기존 상세 핸들러와 같다).
- `vite.config.ts` `apiRoute()`에 새 경로를 매핑하고 `vercel.json` rewrite를 함께 추가한다(함정 1).

### 4-5. 화면 파일

- `client/src/pages/MyProjects.tsx` → 현황판(정렬·D-day·진행). `components/my/ProjectCard.tsx`를 확장한다.

- "진단받기"는 `/analyze`의 제출 로직(멱등성 키 생성, 202 접수증, `/analysis-pending` 이동)을 **재사용**한다. 호출자가 둘이 되므로 공용 함수로 꺼낸다(`client/src/lib/analysisRequest.ts` 근처).
- 라우트는 `App.tsx`에 이미 있는 `/my`, `/my/:projectId`를 그대로 쓰고 새 라우트는 만들지 않는다.
- 스타일: 기존 Tailwind/Radix. 그라데이션 버튼·알약 배지 같은 "AI 티" 장식은 쓰지 않는다.

## 4A. P2 경험 추천 — 상세

### 4A-1. 사용자에게 보이는 동작

- **내 경험 탭(P1)에서 경험에 이름을 붙인다.**
  - "이 경험을 한 줄로 부르면?" — 키워드든 문장이든 본인이 짓는다. 예: "손님 불만을 단골로 바꾼 3개월".
  - 나머지: 기간, 상황, 내가 판단하고 한 일, 달라진 것, 키워드(최대 5개).
  - P1 계획의 `Experience.title`이 이 "한 줄 이름"이다. 스키마는 그대로, 화면 문구만 바꾼다.
- **지원서 작업 화면에 "어떤 경험을 쓸까?" 버튼.**
  - 누르면 지원서의 **모든 문항을 한 번에** 보고 추천한다(문항 사이 겹침을 피하려면 한꺼번에 봐야 한다).
  - 문항마다 보여 주는 것:
    - 추천 경험 1~2개 (경험의 한 줄 이름 그대로)
    - 왜 이 경험인지 한 줄
    - 쓸 각도 불릿 2~3개 (예: "갈등 상황보다 내가 바꾼 기준에 무게") — **완성 문장 아님**
  - 전체 경고:
    - 같은 경험이 두 문항에 추천되면 "겹침"을 표시하고 대안을 제시한다.
    - 맞는 경험이 없는 문항은 "이런 경험이 있으면 적어 두세요"라고 어떤 종류의 경험인지 알려 준다(지어내지 않는다).
  - 결과는 지원서에 저장해서, 다시 열어도 횟수가 들지 않는다. 경험이나 문항을 바꾼 뒤에 다시 받을 수 있다.
- **조건**: 로그인, 경험 1개 이상, 문항 1개 이상. 경험이 없으면 버튼 대신 "내 경험 적으러 가기"를 보여 준다.
- **무료 하루 N회** (기본안 5회, 사용자 확정 필요). 다 쓰면 "내일 다시 받을 수 있어요".

### 4A-2. 비용

- 가벼운 모델(`gemini-2.5-flash-lite`, 공고 불러오기·문항 나누기와 같은 모델)을 한 번 부른다. 입력은 문항+경험 요약 몇천 자, 출력은 짧은 JSON이라 **한 번에 1~2원 안팎으로 추정**한다(진단 리포트보다 훨씬 싸다). 실제 단가는 구현 때 `geminiUsage`로 첫 호출을 재서 확인한다.
- 하루 N회 제한이 비용 상한 역할을 한다.

### 4A-3. 서버

- **엔드포인트**: `POST /api/account/experience-match`, 본문 `{ projectId }`. 계정 라우터에 얹는다(함수 수 그대로). `vite.config.ts` 매핑도 함께 추가한다.
  - 서버가 직접 지원서 문항과 내 경험을 읽는다(클라이언트가 보낸 경험을 믿지 않는다). 남의 지원서는 404 `NOT_FOUND`.
  - 답변 본문은 보내지 않는다. 문항·글자 수·회사·직무·경험만 보낸다.
- **횟수 제한**: `lib/rate-limit.js`의 `USER_RATE_LIMITS`에 `experienceMatch: { route, limit: N, windowMs: 하루 }`를 추가하고 `consumeUserRateLimit`를 쓴다. 초과 시 기존과 같은 429 `RATE_LIMITED`.
  - **선례**: `lib/job-posting.js`(공고 불러오기)가 이미 "크레딧 안 쓰는 무료 + flash-lite + `USER_RATE_LIMITS.jobPosting` 제한" 구조다. 같은 모양으로 만든다.
  - 모델 호출이 실패하면 횟수를 돌려줄지: 기본안은 **돌려주지 않는다**(제한 버킷에 되돌리기 기능이 없음). 실패율이 높으면 다시 본다.
- **모델 호출**: `lib/model-client.js`의 `callGeminiGenerate` + `parseModelJson`. 결과의 경험 id가 실제 내 경험 id인지 서버에서 걸러 낸다(모델이 지어낸 id 제거).
- **프롬프트**: `shared/prompts/experienceMatchPrompt.js`에 단일 정의. "문장을 쓰지 말 것"은 규칙 문단이 아니라 **응답 스키마 필드 설명**에 쓴다(flash-lite는 규칙 섹션보다 필드 설명을 따른다).
- **저장**: `Project`에 `experienceMatch Json?`과 `experienceMatchedAt DateTime?`을 추가한다(마이그레이션 1개, 추가만).
- **시간**: 계정 함수는 `maxDuration` 설정이 없다(기본값). flash-lite 짧은 출력이면 충분할 것으로 보지만, 구현 때 실측하고 모자라면 `vercel.json`에 계정 함수 `maxDuration`을 추가한다.
- **로그 금지**: 경험 본문·문항·모델 응답은 로그·감사 이벤트에 남기지 않는다.

### 4A-5. P2 검증

- API: 비로그인 401, 남의 지원서 404, 경험 0개·문항 0개 400, 하루 한도 초과 429, 모델 응답의 가짜 id 제거, 저장 후 재조회 시 모델 미호출. 모델은 주입한 가짜로 테스트한다(실제 호출 금지).
- 프롬프트: 스키마 필드 설명에 "문장 금지"가 있는지 테스트로 고정한다.
- 화면: 경험 없을 때 안내, 결과 표시(이름·이유·불릿), 겹침·빈칸 표시, 한도 초과 문구.
- 로컬 실측: 실제 경험 5개·문항 3개로 결과가 **문장이 아니라 불릿**인지, 겹침을 피하는지 눈으로 확인한다.

## 5. P3 공고 보드 — 상세

### 5-1. 사용자에게 보이는 동작

- **`/postings` 목록** (로그인 불필요)
  - 접수 중인 공채를 마감 임박순으로 보여 준다. 카드: 회사/그룹, 계열사 수, 마감 D-day, 문항 공개 여부.
  - 마감된 공고는 기본으로 숨기고 "마감된 공고 보기"로 연다.
- **`/postings/:slug` 상세** (로그인 불필요)
  - 접수 기간, 계열사·직무, 전형 절차, 지원 자격 요약, 자소서 문항(글자 수 포함), 원문 채용 사이트 링크
  - 짧은 해설: 어디에 넣을지 고르는 기준, 문항별 출제 의도
- **"이 공고로 지원서 만들기"**
  - 계열사·직무를 고르면 해당 문항이 들어간 지원서(P1)가 만들어지고 작업 화면으로 이동한다.
  - 비로그인이면 로그인 뒤 이어서 만든다. 기존 "로그인 뒤 자동 제출" 패턴(`useSubmitAfterLogin`)을 참고한다.
  - 문항이 아직 공개되지 않은 공고는 "문항 공개 전" 표시와 함께 빈 지원서(회사·직무·마감만)를 만들고 직접 입력하게 한다.

### 5-2. 데이터: 파일 기반 (추천) vs DB

| | **파일 기반 (추천)** | DB + 관리자 화면 |
|---|---|---|
| 저장 | `client/content/postings/<slug>.md` (frontmatter + 해설 본문) | 새 테이블 + 관리자 CRUD |
| 등록 | 블로그 공고 루틴이 초안 md를 함께 만들고 → 사용자 검토 → 푸시 | 관리자 화면에서 입력, 배포 불필요 |
| SEO | 가이드와 같은 빌드 프리렌더·sitemap 경로를 그대로 탄다 | 프리렌더하려면 빌드 때 DB를 읽어야 하고, 새 공고마다 재배포가 필요해 결국 같다 |
| 함수 | 추가 없음(공개 읽기 API 불필요) | 공개 읽기 경로 필요 |
| 단점 | 공고 하나 올릴 때마다 푸시(승인)가 필요하다 | 만들 게 많다(모델·관리자 UI·공개 API) |

**추천: 파일 기반.**
- 이미 검증된 가이드 파이프라인을 그대로 쓴다: `client/content/guides/*.md` → `lib/guides.ts`(import.meta.glob) → `entry-server.getPrerenderPages()` → sitemap/RSS.
- 공고는 블로그 루틴이 이미 정리하고 있어서, 등록 비용은 "md 하나 더 + 푸시 승인"이다.
- 나중에 공고가 하루 여러 개로 늘면 DB로 옮긴다.

## 6. P4~P5 개요 (각 단계 착수 때 별도 상세 설계)

- **P4 경험 자동 추출 + 4단 뼈대**
  - 직접 입력(P1)은 이미 있다. 여기서는 붙여넣은 자소서나 지난 분석에서 경험 카드 초안을 flash-lite로 뽑아 준다. 사용자가 확인·수정해서 저장한다(한 줄 이름도 사용자가 고친다).
  - 경험 추천(P2) 결과 위에 4단 뼈대(직무가 하는 일 → 필요 역량 → 내 근거 → 들어가서 할 일)를 **불릿으로**, 첫 문장 방향 한 줄을 얹는다.
  - 무료 하루 N회. `USER_RATE_LIMITS`에 정책을 추가한다. 엔드포인트는 계정 라우터.
  - **문장 생성 금지**는 스키마 필드 설명에 쓴다. 프롬프트는 `shared/prompts/`에 단일 정의한다.
- **P5 진단 강화**
  - **의도 vs 인상**: 사용자의 "기억되고 싶은 한 문장"을 저장하고, 리포트 첫 섹션에 의도한 모습 / 읽힌 모습 / 차이를 만든 문장을 보여 준다.
    - 스키마에 `intendedVsPerceived`를 추가하고, 해시에 반영한다.
    - `reportPrompt.singleSource.test.ts`를 함께 확인한다.
  - **에디터 옆 진단**: feedbackCards 원문 하이라이트를 작업 화면 본문 위에 겹친다.
  - **기업 분석 연결**: 기업 분석 "자소서 소재" 사용 여부를 확인한다.

## 8. 남은 위험

- **analyze 요청에 `projectId`를 넣는 것은 크레딧·멱등성 경로를 건드린다.**
  - 소유권 확인을 트랜잭션 안에서 하고, 실패 시 예약 전에 끊는 순서를 테스트로 고정한다.
- **자동 저장은 요청이 잦다.**
  - 디바운스 + 변경 없을 때 전송하지 않기로 줄인다.
  - Supabase 연결 수에 영향이 없는지 지켜본다.
- **범위**: P1 약 1~2주, P2(경험 추천) 약 1주, P3(공고 보드) 약 1주. 공채 시즌 안에는 P1·P2까지가 현실적이고, 공고 보드는 시즌 막바지나 다음 시즌(상반기 공채) 대비로 본다.
- **경험 추천 품질**: 경험을 짧게 적으면 추천도 얕아진다. 입력 폼 안내 문구(예시)가 품질을 좌우한다.
- **공고 보드의 신선도**는 블로그 루틴과 푸시 승인 속도에 달려 있다.
