# 내 경험으로 초안 쓰기 — 설계 (2026-10-05)

> 근거: `docs/superpowers/specs/2026-10-05-사용자-기대와-재방문-이유.md` (v2)
> 서비스 목표: 경험을 나열 → 공고에 맞게 조합한 초안 → 고쳐서 → 완성본 분석.
> 이 스펙은 그중 **비어 있는 한 칸(경험 → 초안)**만 다룬다.

## 1. 결정 사항 (10-05 사용자 승인)

| 항목 | 결정 |
| --- | --- |
| AI 작성 범위 | **초안까지 쓴다.** 단 "부풀리지 않는 AI" — 사용자가 적은 경험의 사실로만 쓴다 |
| 과금 | **무료.** 계정당 하루 2개(문항 초안 기준). 다시 만들기도 1개로 센다. 실패한 생성과 "경험 부족" 응답은 세지 않는다 |
| 경험 선택 | **AI가 골라 바로 초안을 쓴다.** 고른 경험과 이유를 함께 보여 준다 |
| 공고 | **선택.** 붙이면 공고 기준으로 쓰고, 없으면 회사·직무명만 쓴다. 회사에 대한 사실은 지어내지 않는다 |
| 생성 단위 | **문항 하나씩**, 기다리지 않는 동기 호출(방식 A) |

**성공 기준**
- 경험이 1개 이상 있는 사용자가 작업실 문항에서 버튼 한 번으로 초안을 받는다.
- 초안 속 숫자는 모두 인용한 경험(또는 공고)에 있던 숫자이거나 `[실제 수치]` 빈칸이다. 서버 테스트로 보장한다.
- 초안 문장마다 어느 경험에서 왔는지 보인다.

## 2. 사용자 흐름

```
내 지원서 → 문항 카드 → [내 경험으로 초안 쓰기]
   ├─ 경험 0개 → "경험부터 적어 주세요" + 내 경험 탭 링크 (호출 없음)
   └─ 생성 중(약 20~30초) "경험을 고르고 있어요…"
        ├─ 성공 → 미리보기
        │    · 고른 경험 칩 + 고른 이유 한 줄
        │    · 문장마다 출처 칩(경험 이름), 출처 없는 경험 문장은 회색 경고
        │    · 빈칸([실제 수치] 등)은 노란색
        │    · 글자 수 / 문항 제한
        │    · [이 초안으로 채우기] [다른 경험으로 다시] [닫기]
        ├─ 경험 부족 → "이 문항엔 ○○ 같은 경험이 필요해요. 있나요?" + 내 경험 탭 링크
        └─ 한도 초과 → "오늘 무료 초안 2개를 다 썼어요. 내일 오전 9시에 다시 생겨요."
```

- **이 초안으로 채우기**: 답 칸이 비어 있으면 바로 넣는다. 이미 글이 있으면 "지금 쓴 글을 바꿀까요?"를 한 번 묻는다. 채운 뒤에는 지금처럼 자동 저장되고, 사용자가 자유롭게 고친다.
- **다른 경험으로 다시**: 방금 고른 경험을 "피할 경험"으로 넘겨서 다시 만든다(1개 차감).
- 채운 뒤 문항 카드에 "초안에 쓴 경험: A, B" 칩을 남긴다.
- **공고 붙이기(선택)**: 작업실 머리말에 "공고 붙여넣기" 버튼을 둔다. 이미 있는 공고 요약(`POST /api/analyze/posting`)을 그대로 쓰고, 돌려받은 공고 ID를 지원서에 저장한다.
- **입구 한 줄**: `/analyze`의 "아직 자소서가 없다면" 줄에 "내 경험으로 초안 쓰기 →"(`/my`) 링크를 하나 더한다.

## 3. 부풀림 방지 — 약속이 아니라 검사

AI에게 지시만 하지 않는다. **서버가 결과를 검사하고 고친다.** 지시는 어겨질 수 있지만 검사는 테스트로 보장할 수 있다.

| 장치 | 어디서 | 내용 |
| --- | --- | --- |
| 사실 제한 지시 | 프롬프트 | 넘겨준 경험의 상황·한 일·결과에 있는 사실만 쓴다. 없는 성과·숫자·역할·기간은 만들지 않고 `[실제 수치]`·`[구체적 행동]` 같은 빈칸을 남긴다. 공고가 없으면 회사 고유 사실은 쓰지 않고 필요하면 `[회사 조사 필요]`를 남긴다 |
| 경험 부족 신호 | 프롬프트 + 서버 | 맞는 경험이 없으면 초안 대신 `needs_more`와 "어떤 경험이 필요한지" 한 문장을 돌려준다 |
| **출처 검사** | 서버 | 문장의 `sourceIds` 중 그 사용자의 경험 ID가 아닌 것은 버린다. 출처가 비게 된 경험 문장은 `unsourced`로 표시한다 |
| **숫자 검사** | 서버 | 초안의 숫자 토큰(숫자 + 단위: %, 명, 배, 원, 만, 억, 건, 개, 회, 시간, 일, 주, 개월, 년, 위, 점)을 찾는다. 그 문장이 인용한 경험 글(직무·계획 문장은 공고 글)에 같은 숫자가 없으면 **`[실제 수치]`로 바꾼다.** 비교할 때 쉼표·공백은 무시한다 |
| 빈칸 표시 | 클라이언트 | `[…]`(20자 이내) 패턴을 노란색으로 표시한다 |

## 4. 글의 뼈대 (프롬프트)

창업자가 멘토링에서 25회 넘게 쓴 순서 공식을 뼈대로 쓴다.

1. 이 직무가 하는 일(공고가 있으면 공고 기준, 없으면 직무 일반론)
2. 그 일에 필요한 역량
3. 나에게 그 역량이 있다(한 줄 컨셉)
4. 근거가 되는 경험(1~2개, 나열 금지)
5. 입사 후 이걸 하겠다

- **길이**: 문항 글자 수 제한의 약 75%로 쓴다(10-06 실측에서 모델이 목표보다 5~25% 길게 써 90%→75%로 낮춤). 제한이 없으면 700자. 서버는 자르지 않고 글자 수만 돌려준다.
- **경험 수**: 문항당 1~2개. "다 잘한다"로 흐려지는 나열을 막는다(멘티가 막힌 곳 2위).
- **말투**: 리포트 문장 취향 메모를 따른다(과장 동사 금지). 문장 예시는 프롬프트에 넣지 않는다. 모델이 예시 단어를 베끼기 때문이다(`prompt-rules-vs-structure` 메모).
- **정의처**: `shared/prompts/draftPrompt.js` 한 곳에 둔다.

**모델 응답 형식(JSON)**

```json
{
  "status": "ok | needs_more",
  "chosen": [{ "experienceId": "uuid", "reason": "한 줄" }],
  "sentences": [{ "text": "...", "kind": "job | experience | plan", "sourceIds": ["uuid"] }],
  "needMore": "status=needs_more 일 때만, 필요한 경험 한 문장"
}
```

## 5. 서버

**엔드포인트**: `POST /api/analyze/draft` → `api/analyze.js?draft=1`
- 함수 12개가 꽉 차 있어서 `selectAnalyzeHandler`에 `draft` 분기를 추가한다(split → posting → **draft** → kind 순서).
- `vercel.json` rewrite와 `vite.config.ts`의 `apiRoute()`에 같은 매핑을 추가한다(함정 1).

**요청**: `{ projectId, prompt, charLimit?, avoidExperienceIds?: string[] }`
- 문항 문구를 클라이언트가 보낸다. 아직 저장 안 된 문항에서도 쓸 수 있게 하려는 것이다. 검증은 `lib/application-drafts.js`의 문항 규칙(300자)을 재사용한다.

**처리 순서**(`lib/experience-draft.js`, 의존성 주입 팩토리 — `lib/job-posting.js`와 같은 모양)
1. `requireAuthenticatedUser` → `requireActiveApplicationUser`
2. 프로젝트 소유 확인(아니면 404)
3. 사용자 경험 조회(`updatedAt` 최신순 최대 40개, 각 칸 400자로 줄임). 0개면 `NO_EXPERIENCES`(422)로 끝낸다. 횟수는 차감하지 않는다
4. 같은 지원서의 다른 문항 `draftExperienceIds`와 `avoidExperienceIds`를 합쳐 "피할 경험"으로 만든다(약한 지시)
5. 공고 요약: 프로젝트에 `jobPostingId`가 있으면 소유 확인 뒤 `summaryJson`·`rawText`(앞 3,000자)를 쓴다
6. `consumeUserRateLimit(policy: experienceDraft)` — 한도 초과면 429 `RATE_LIMITED`
7. `callGeminiGenerate`(gemini-2.5-flash, JSON 응답, 데드라인 60초) → `parseModelJsonTolerant`
8. 정규화: 출처 검사 → 숫자 검사 → 글자 수 계산
9. 모델 오류·파싱 실패면 6에서 쓴 횟수를 되돌리고(`refundUserRateLimit`, 새 함수) 502 `DRAFT_FAILED`

**응답 200**
```json
{
  "status": "ok",
  "chosen": [{ "experience_id": "…", "title": "…", "reason": "…" }],
  "sentences": [{ "text": "…", "kind": "experience", "source_ids": ["…"], "unsourced": false }],
  "draft_text": "문장을 이어 붙인 전문",
  "char_count": 612,
  "replaced_numbers": 1,
  "remaining_today": 1
}
```
`status: "needs_more"`일 때는 `need_more` 문장만 돌려주고 쓴 횟수를 되돌린다. 하루 2개뿐이라, 초안을 못 받은 시도까지 세면 첫 경험이 나빠진다.

**횟수 제한**: `lib/rate-limit.js`에 `experienceDraft: { route: "experience-draft", limit: 2, windowMs: 24h }`를 둔다. 창은 UTC 자정 기준이라 **KST 오전 9시에 초기화**된다.

**로그**: 경험 본문·문항·초안 텍스트를 로그와 감사 이벤트에 남기지 않는다. 요청 ID, 결과 상태, 소요 시간, 바꾼 숫자 개수만 남긴다.

**토큰 기록**: `TokenUsage`는 `analysisId`가 필수라 이번에는 남기지 않는다(공고 요약·문항 분리와 같은 상태). 원가 추적은 남은 일로 둔다.

시즌권·잠금 해제·가격 개편, 기업별 페이지, 면접 준비 모드, 이력서에서 경험 자동 추출, 문항 여러 개 한 번에 생성, 랜딩 문구 개편, 토큰 원가 기록.

## 10. 남은 위험

- **하루 2개는 빡빡하다.** 지원서 하나(문항 3~5개)를 채우는 데 2~3일이 걸린다. "다른 경험으로 다시"도 1개를 쓴다. 사용 기록을 보고 조정한다(설정값 한 줄).
- **숫자 검사는 숫자만 막는다.** "팀장으로서" 같은 역할 부풀림은 프롬프트 지시와 출처 표시에 기댄다. 실제 초안 5건 이상을 사람이 읽어서 확인한다.
- **동기 호출 시간**: Flash 기준 20~30초로 예상한다. 60초 데드라인을 넘는 일이 잦으면 사고(thinking) 예산을 줄인다.
- **문항 간 중복 회피는 약하다.** 피할 경험을 지시로만 넘긴다. 경험이 적은 사용자는 같은 경험이 반복될 수 있다.
